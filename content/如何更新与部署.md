本页记录两件事：**平时怎么更新**，以及**要真正自动化时怎么把环境装起来**。

> **所有细节以对应条目为准，本页只管流程。** 内容改法见各条目页；构建脚本说明见 `README.md`。

## 一、日常更新（现在就能用）

改完设定后的最小流程：

1. 编辑 `wiki/content/` 下的 `.md`
2. 在本目录下运行 `node build.mjs`（或双击 `打开wiki.bat`）
3. 把 `wiki/site/` 里的**全部文件**重新上传到托管平台

上传方式二选一：

- **拖拽**：把 `wiki/site/` 里的文件全选拖进托管平台的上传区域
- **压缩包**：把 `site/` 里的文件压成 zip（**`index.html` 必须在压缩包根层**）再上传

> ⚠️ **`site/` 是构建产物，每次构建都会被整个清空重建。** 任何需要长期存在的文件（如 `robots.txt`）都必须写进 `build.mjs`，手工放进 `site/` 会在下次构建时消失。

## 二、为什么要自动化

手动流程里唯一麻烦的一步是"上传"。要做到**改完只需一条命令**，需要把内容托管到代码仓库，让平台自己拉取、自己构建、自己发布。

前置条件（**必须先装**）：

| 工具 | 用途 | 下载地址 |
|---|---|---|
| **Git** | 把改动推送到仓库 | `git-scm.com` |
| **Node.js**（LTS 版） | 本地跑构建脚本；自动化后由平台跑，但本地仍需 | `nodejs.org` |

> ### 本机实际安装情况（2026-09-17 已装好）
>
> 本机**没有**用官网安装包，而是装了**便携版**——无需管理员权限、不写注册表、不改系统 PATH、可整目录删除：
>
> | 工具 | 版本 | 位置 |
> |---|---|---|
> | Git | 2.55.0 | `C:\Users\cyt\Desktop\DSH-tools\PortableGit\cmd\git.exe` |
> | Node.js | v24.21.0 | `C:\Users\cyt\Desktop\DSH-tools\node-v24.21.0-win-x64\node.exe` |
> | npm | 11.19.0 | 同上目录（随 Node.js 附带） |
> | GitHub CLI | 2.101.0 | `C:\Users\cyt\Desktop\DSH-tools\gh\gh.exe` |
>
> **因为没改系统 PATH，在普通命令行里敲 `git` / `node` 会找不到。** 用这两个入口：
>
> - **`DSH-tools\打开命令环境.bat`** —— 打开一个已配好 PATH 的命令窗口（仅该窗口有效）
> - **`DSH-wiki\一键推送.bat`** —— 一键完成「构建 → 提交 → 推送」
>
> > 注意：DSH Desktop 自带的那个 `node`（`ELECTRON_RUN_AS_NODE=1` 的 Electron）**不含 npm**，不能用来装包。

验证安装：

```bash

npm -v               # 期望输出 10 或更高
```

## 三、建立仓库（隔离是第一原则）

### 3.1 首要安全要求：绝不把 `config.json` 提交进仓库

`qq-bridge/config.json` 含有 `snowluma.accessToken`、`ownerQQ`、QQ 群号白名单等**敏感信息**（该文件已在 `qq-bridge/.gitignore` 中，但**不要依赖这一点**）。

**推荐做法：为 wiki 单建一个独立仓库**，物理上与 `qq-bridge` 隔离，从根上杜绝误提交：

```
DSH-wiki/                    ← 新仓库根目录（可以就建在桌面）
├── .gitignore
├── build.mjs
├── README.md
├── 打开wiki.bat
└── content/                 ← 24 篇设定源文件（含本页）
```

即：把 `qq-bridge/wiki/` 里的这四样复制到仓库根目录，`site/` **不要**复制（它是产物）。

`.gitignore` 内容：

```
# 构建产物：由平台自动生成，不入库
site/

# 编辑器 / Office 临时文件
~$*
*.tmp
*.bak
```

### 3.2 建仓库并首次推送

1. 登录 `github.com` → **New repository**
2. 仓库名例如 `DSH-wiki`，可见性选 **Private**（未公开的设定稿建议私有）
3. **不要**勾选 "Add a README file"（本地已有）
4. 建好后在本地仓库目录执行：

```bash
cd  C:\Users\cyt\Desktop\DSH-wiki
git init
git add .
git commit -m "初始化：世界观 wiki（24 篇）"
git branch -M main
git remote add origin https://github.com/<你的用户名>/DSH-wiki.git
git push -u origin main
```

> 首次 `push` 会要求登录。GitHub 已不支持账号密码，需用 **Personal Access Token**：`Settings → Developer settings → Personal access tokens`，生成后**当作密码**粘贴。或安装 **GitHub CLI**（`gh auth login`）会更省事。

推送后**务必去 GitHub 网页确认仓库里没有 `config.json`**，只有 `wiki/` 下的内容。

## 四、连接平台（二选一）

### 方案甲：Netlify 持续部署

1. 登录 Netlify → **Add new site → Import an existing project**
2. 选 **GitHub**，授权后选中 `DSH-wiki` 仓库
3. 构建配置：
   - **Build command**：`node build.mjs`
   - **Publish directory**：`site`
   - **Base directory**：留空
4. 点 **Deploy**。之后每次 `git push`，Netlify 自动重建并发布

### 方案乙：GitHub Pages（更省事，无需 Netlify）

1. 仓库页 → **Settings → Pages**
2. **Source** 选 `Deploy from a branch`，分支选 `main`，目录选 `/ (root)`
3. 但注意：Pages 直接发布仓库内容，而源文件必须**先构建**，所以更稳的做法是加一个工作流文件 `.github/workflows/deploy.yml`：

```yaml
name: Build and Deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: node build.mjs
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site
  deploy:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

然后在 **Settings → Pages → Source** 选 **GitHub Actions**。

> 两个平台的选择：**Netlify** 有现成的拖拽/导入界面、部署记录与一键回滚；**GitHub Pages** 少一个平台、少一次授权，但需要上面这个工作流文件。二者都免费。

## 五、接好之后的日常流程

```bash
# 1. 改内容（编辑 wiki/content/*.md）
# 2. 本地预览
node build.mjs --serve           # 然后浏览器打开 127.0.0.1:8899

# 3. 推送
git add .
git commit -m "更新：<这次改了什么>"
git push
```

推送后平台自动构建并发布，无需登录平台界面。**这就是"自动同步"的完整形态。**

## 六、常见问题

| 现象 | 原因与处理 |
|---|---|
| `git` / `node` 命令找不到 | 装完没开新命令行窗口；或安装时没勾选加入 PATH，重装并勾选 |
| push 时提示认证失败 | GitHub 不支持密码登录，改用 Personal Access Token 或 `gh auth login` |
| 平台构建报错找不到文件 | 构建命令/发布目录填错。仓库根就是这个 wiki 目录时，务必是 `node build.mjs` 与 `site`（相对于仓库根） |
| 线上首页 404 | 发布目录填成了仓库根，或压缩包多套了一层目录；`index.html` 必须在发布目录**根层** |
| 搜索功能失效 | `search-index.js` 没上传成功（它是构建产物，确认发布目录含该文件） |
| 构建后 `robots.txt` 不见了 | 它是 `build.mjs` 生成的，确认用的是最新版脚本 |
| 担心被搜索引擎收录 | `build.mjs` 已生成 `robots.txt` 且每页带 `noindex`；若要**允许**收录，删掉脚本里这两处 |

## 七、实测踩过的坑（2026-09-17 首次部署时全部遇到）

以下问题都真实发生过，且**原因都不在"操作步骤"上**，重装或换机器时大概率会再遇到。

### 7.0 部署完成的判定标准（先看这条）

站点建好后，「**算不算成功**」不要靠界面文字判断，直接**从外部访问一次**，看 HTTP 状态码：

| 状态码 | 含义 | 该怎么办 |
|---|---|---|
| **200** | 部署成功且对外可访问 | ✅ 完成 |
| **401 / 403** | **站点存在、内容已发布，但被访问控制挡住** | 项目可见性设为私有 → 需改为公开，见 7.5 |
| **404** | 站点不存在，或部署失败 | 去 Deploys 面板看构建日志 |
| 连不上 | 域名错误或部署尚未完成 | 检查项目名 |

> **404 与 401 的区别很关键**：前者是"没建起来"，后者是"建好了但别人进不去"。界面显示「部署成功」也可能仍然是 401。

### 7.1 批处理文件必须是 GBK 编码 + CRLF 换行

**现象**：双击 `.bat` 一闪而过、什么都没输出；或报一堆 `'xxx' is not recognized as an internal or external command`；甚至出现字符被吞掉（如 `setlocal` 变 `offsetlocal`、`echo` 变 `cho`）。

**原因**：中文 Windows 控制台默认代码页是 **936（GBK）**。若 `.bat` 存成 **UTF-8**，cmd 会按 GBK 解析 UTF-8 的中文，**行结构被打断**；若同时是 **LF 换行**（而非 CRLF），cmd 的行读取会进一步错位，尤其在 `if ... ( ... ) else ( ... )` 括号块里。

**处理**：

- `.bat` 一律存为 **GBK 编码 + CRLF 换行**
- **`chcp 65001` 救不了** —— 它生效时 cmd 已经解析完那些行了
- 用 `-Encoding Byte` 检查：首字节应为 `64 65 63`（`@ec`），不能是 `239 187 191`（UTF-8 BOM）；CR 与 LF 数量必须相等

> ⚠️ **`.md` 源文件必须保持 UTF-8**（`build.mjs` 按 UTF-8 读取）。**只有 `.bat` 用 GBK**，不要搞反。

### 7.2 不要用 Word / WPS 打开 `.md` 文件

**现象**：构建时多出一个垃圾页面（如 `~$何更新与部署.html`），页面总数虚增；文件被独占锁定，无法编辑或写入。

**原因**：Word 会为打开的文件生成 `~$` 前缀的临时锁文件，并**独占锁定**原文件。该锁文件同样以 `.md` 结尾，会被 `build.mjs` 当作一篇正文处理。

**处理**：

- 编辑 `.md` 请用**记事本、VS Code** 等纯文本编辑器
- `build.mjs` 已加固：会跳过 `~$*` 与 `.*` 开头的文件并打印跳过提示
- 若已产生锁文件，关闭 Word 后删除该文件

### 7.3 git 不读系统代理，但 `gh` 会读

**现象**：`gh repo create` 成功建了仓库，但 `git push` 失败 —— 报 `Failed to connect to github.com:443`、`Connection was reset` 或长时间超时。

**原因**：开着代理（本机为 `127.0.0.1:7890`）时，**`gh` 自动读取系统代理设置，而 `git` 不会**，它去直连 GitHub —— 直连在内地通常不通。于是出现"建仓库成功、推送失败"这种迷惑现象。

**处理**（已写入 `一键推送.bat`，它会自动读系统代理并交给 git）：

```bash
git config --global http.proxy  http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890
```

> 若日后关掉代理软件，记得清掉，否则 git 会连不上：
> `git config --global --unset http.proxy` 与 `--unset https.proxy`

### 7.4 `gh` 的 token 必须含三个 scope，且要接通 git 凭据

**现象**：token 明明有效（能访问 API），`gh auth login --with-token` 却报
`error validating token: missing required scope 'read:org'`；或 `git push` 报
`could not read Username for 'https://github.com'`。

**原因**：

- `gh` 官方要求 classic token 至少有 **`repo`、`read:org`、`gist`** 三个 scope。只勾 `repo` 会被拒。
- `gh` 把 token 存在系统凭据库（keyring）里，**git 默认不知道去取**。

**处理**：

- 生成 token 时**三个 scope 都要勾**；已有的 token 可以直接进去补勾后 `Update token`，**token 字符串不变**
- 跑一次 `gh auth setup-git`，让 git 通过 gh 取凭据（`一键推送.bat` 已内置）
- 预检技巧：用 curl 直接问 GitHub API，能一次区分"token 无效"与"scope 不足"

```bash
curl -s -D - -o /dev/null -w "%{http_code}" \
  -H "Authorization: Bearer <token>" \
  -H "User-Agent: dsh" https://api.github.com/user
```

### 7.5 Netlify 的界面术语已改，且新建项目默认可能不公开

**术语变更**：新版 Netlify 把 **Sites 改称 Projects**，因此找不到旧教程里的「Add new site」。

**当前路径**：`app.netlify.com` → **Projects** → **Add new project** → **Import from an existing repository** → 选 GitHub → 选仓库。

**可见性坑（重要）**：Netlify 现在是 **credit-based 计划**，若团队设置了默认私有，新建项目会**默认不对外公开**，外部访客一律收到 **401**。界面顶部会显示 **`Make public`** 按钮，就说明当前是私有状态。

- 想让**任何人都能打开**：在项目总览页点 **`Make public`**
- 只想给团队看：保持私有

> **代码仓库与项目可见性是两件独立的事**：GitHub 上的 `DSH-wiki` 仓库**应保持 Private**（那是源文件与提交历史）；Netlify 项目**改为 public 完全安全** —— 访客只能看到渲染好的网页，看不到 `content/` 源文件，也看不到 git 历史。

**构建配置**（Import 时填写）：

| 字段 | 值 |
|---|---|
| Build command | `node build.mjs` |
| Publish directory | `site` |
| Base directory | 留空 |

改完可见性后，**务必按 7.0 的方法从外部访问一次确认状态码为 200**。

详见 [Netlify 官方文档 · Add new project](https://docs.netlify.com/manage/projects/add-new-project/)。
